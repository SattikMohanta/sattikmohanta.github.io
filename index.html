osTicket AI Triage Agent

  • Python
  • FastAPI
  • Claude API
  • osTicket
  • Splunk
  • Docker
  • Slack
  • PagerDuty

Helpdesk queues mix routine IT requests with early signs of real incidents. A compromised account or phishing report can sit unread behind printer tickets. This agent classifies each new ticket as it arrives, enriches critical incidents with related events from Splunk, and escalates security incidents to a human responder.

Built and tested in a lab, using BOTSv3 training data and fictional users. It has not run on a real helpdesk.

How it handles failure

  • The page goes first. The PagerDuty page goes out before any call to Splunk, since Splunk can be struggling during the same incident. With Splunk hanging in a test, the page was accepted 0.5 seconds after classification.
  • Pages are confirmed. PagerDuty accepts pages through dead routing keys and opens no incident, so the agent checks that each page opened one and reports any that didn't.
  • It never invents a label. A ticket Claude can't classify goes to the review Slack channel with the failure type and no classification label, because a guessed label could quietly mark an incident as routine.
  • It survives a crash. A SQLite store records each ticket and every finished action, so a restarted agent runs only what's left. I tested it by killing the agent with SIGKILL mid‑ticket, and it finished the ticket with no new delivery.

Tested: 35 of 36 labeled test tickets in each of nine runs, plus 398 verification checks, 228 of them run in CI on every push.

Splunk SIEM Lab: CoinMiner Investigation

  • Splunk
  • SPL
  • MITRE ATT&CK
  • NIST CSF
  • NIST 800-53
  • CIS Controls v8
  • CyberChef

Investigated a drive-by cryptomining attack in Splunk, working from 1.9 million events across 107 sourcetypes. Traced it to a trusted industry forum serving a CoinHive miner, identified the one workstation that mined for 26 minutes, and found the root cause in a publicly writable AWS S3 bucket.

Built on BOTSv3, Splunk's public training dataset about a fictional brewing company.

How I investigated

  • I ruled out a false lead. The busiest DNS domain looked like beaconing from 14 hosts. Follow-up didn't tie it to the attack, so I pivoted to a CPU spike, which led to the miner.
  • I turned a 10-second gap into a detection recommendation. Symantec blocked the miner on one host at 09:37:40. Ten seconds later, Chrome on a workstation with no Symantec detections hit 100% CPU. I recommended treating one host's block as a warning for other hosts that visited the same site.
  • I worked around a visibility gap. Process CPU data existed only for the affected workstation, so I checked every host's DNS instead. No other host contacted the mining service.

Delivered: 21 documented SPL queries, three proposed detection rules each rated for false positive risk, findings mapped to MITRE ATT&CK, NIST CSF, NIST 800-53 and CIS Controls v8, an IOC file with current threat context, and a business impact analysis covering possible PCI DSS and HIPAA exposure.
